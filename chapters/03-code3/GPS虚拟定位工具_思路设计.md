# GPS 虚拟定位工具 · 思路设计

> 目标：做一款轻量化的手机端工具，让手机 GPS 按照用户指定的地点/路线"移动"。
> 文档定位：立项前的技术可行性 + 架构思路，不含具体代码实现。

---

## 一、先定平台：这决定了产品能不能成立

| 平台 | 可行性 | 技术路径 | 代价 |
|---|---|---|---|
| **Android** | ✅ 可行 | 官方 Mock Location 机制（`LocationManager` 的 test provider） | 免 root，需在"开发者选项 → 选择模拟位置信息应用"里授权本应用 |
| **iOS** | ❌ 无公开 API | A. 连接电脑，通过 USB 下发模拟位置（开发者模式 + GPX / pymobiledevice3）<br>B. 越狱 + 定位插件 | 都离不开电脑或越狱，做不到"纯手机端轻量工具" |

**结论：MVP 只做 Android。** iOS 若要做，形态是"电脑端辅助工具"，与本项目"手机上的轻量化工具"定位冲突，建议放二期或直接放弃。

---

## 二、技术内核：假位置是怎么"进"手机的

Android 提供了一套用于测试定位类 App 的官方接口，我们的工具本质就是把它产品化：

```
LocationManager.addTestProvider(...)      // 注册一个假的定位源
LocationManager.setTestProviderEnabled()  // 启用
LocationManager.setTestProviderLocation() // 持续写入坐标（1Hz）
```

每次写入需要构造一个完整的 `Location` 对象，字段不止经纬度：

- `latitude` / `longitude` — 核心坐标
- `accuracy` — 精度（米），要随机波动，别恒定
- `speed` / `bearing` — 速度与航向，决定了"看起来在往哪走"
- `altitude` — 海拔
- `time` / `elapsedRealtimeNanos` — 时间戳，必须单调递增
- `satellites` — 卫星数，可选

**关键点：** 只写经纬度、其他字段留空，在目标 App 里会非常可疑（速度为 0、精度为 0）。拟真度靠这些字段一起凑。

## 三、最大的坑：坐标系（中国区必踩）

| 坐标系 | 用在哪 | 说明 |
|---|---|---|
| **WGS-84** | GPS 硬件、系统底层 | 国际标准，真实坐标 |
| **GCJ-02** | 高德、腾讯、Google 中国 | "火星坐标"，国内强制加密偏移 |
| **BD-09** | 百度地图 | 在 GCJ-02 基础上再偏移一次 |

**问题：** 用户在地图上选点是 GCJ-02，但喂给系统必须转成 WGS-84。不做转换，位置在中国境内会偏**几百米**，直接跑到隔壁街区。

**要做的事：**
1. 实现 WGS-84 ⇄ GCJ-02 ⇄ BD-09 三向互转算法
2. 加"是否在中国境内"的判定，境外不偏移，避免坐标被错误加密
3. 整个链路统一用自己的坐标类型封装，禁止裸 `double` 传递经纬度（这是最容易出低级错误的地方）

**地图服务商合规要求：** 国内地图数据必须使用有资质的服务商（高德 / 腾讯 / 百度 / 天地图），不得使用 Google Maps、OpenStreetMap 等未经审图的境外图源。路线规划同理，必须走合规服务商的 API。

## 四、"移动"怎么实现：五种模式

产品功能由模式构成，建议按复杂度递进：

| 模式 | 说明 | 难度 |
|---|---|---|
| 1. 定点 | 固定在一个坐标，不动 | ★ |
| 2. 直线 | A → B 两点之间按速度匀速插值 | ★ |
| 3. 路线 | 沿真实道路走，需调用路径规划 API 拿到 polyline，再沿线推进 | ★★★ |
| 4. 摇杆 | 手动实时控制方向 + 速度，类似游戏手柄 | ★★★ |
| 5. 轨迹回放 | 导入 GPX 文件按原轨迹回放（如跑步轨迹） | ★★ |

**统一抽象：** 上面五种模式底层可以是同一个引擎——一个 1Hz 的 ticker + 一个"当前应该在哪"的计算器 + 一个状态机（`idle` / `moving` / `paused`）。模式只是不同的位置计算器实现。

引擎还需要支持：循环播放、暂停、变速（1x/2x/5x）、终点后停留还是往返。

## 五、拟真度：让轨迹"像真的"

不做这一步，很多校验严格的 App 一眼就能识破。要点：

- **速度不要恒定** — 真实 GPS 速度有抖动，加小幅随机噪声
- **航向角随路径切线变化** — 拐弯时 bearing 要跟着转
- **精度值随机波动** — 在 5~15 米区间浮动，别一直卡在同一个数
- **拐弯处自动减速** — 硬直角拐弯速度不降，非常不自然
- **停顿时不要完全静止** — 原地有几百厘米级微小漂移
- **发送间隔抖动** — 不要严格 1.000s 一次，加几十毫秒抖动

## 六、架构分层

```
┌─ 交互层 ── 地图选点 / 路线绘制 / 控制面板（速度·循环·暂停）
├─ 引擎层 ── 路径规划 + 轨迹插值 + 1Hz 调度 + 拟真抖动
├─ 坐标层 ── WGS-84 ⇄ GCJ-02 ⇄ BD-09 转换与境内判定
├─ 注入层 ── Mock Location Provider 封装（未来可扩展 iOS 桥接）
└─ 保活层 ── 前台服务 + 常驻通知 + 定时唤醒
```

**保活层容易被低估。** 模拟定位需要长时间运行，Android 的后台限制会杀掉普通服务。必须用**前台服务 + 常驻通知**，并且注意各家 ROM（小米/华为/OPPO/vivo）的白名单设置，否则用户会遇到"走了一半就不动了"。

## 七、技术选型建议

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **Kotlin 原生** | 最稳、包体最小、mock 接口直通 | 只能覆盖 Android | ✅ **推荐 MVP 用** |
| Flutter | UI 跨平台 | iOS 依然受限，跨平台收益很低 | ✗ |
| React Native | 同上 | 同上 | ✗ |
| 电脑端工具（adb / pymobiledevice3 驱动） | 能覆盖 iOS | 不是"手机上的工具"，定位不符 | 二期考虑 |

地图 SDK 建议用**高德**或**腾讯**（国内合规、路线规划 API 成熟），遵循所选平台的开放平台接入规范。

## 八、MVP 里程碑

| 阶段 | 交付 | 验收标准 |
|---|---|---|
| **M1** | 定点模拟 | 授权后能把自己定位到任意一点，地图/其他 App 能看到 |
| **M2** | 直线移动 | A→B 按指定速度匀速移动，速度可变 |
| **M3** | 地图选点 + 路线 | 地图上画路线，沿真实道路走；坐标转换正确无偏移 |
| **M4** | 摇杆 + 循环 + 拟真 | 手动控制、循环播放、速度抖动与航向跟随完整 |
| **M5** | GPX 导入导出 + 收藏 | 路线可存可分享可复用 |

建议 M1+M2 先做通，验证"整体链路能不能骗过目标 App"，再投入 M3 的路径规划。

## 九、风险与边界（必须写清）

**技术风险**
- 很多 App 会检测 `Location.isFromMockProvider()` / `isMock`，金融、支付、网约车类会强制校验。**不要对外承诺"能骗过所有 App"** —— 这取决于目标 App 的检测强度。
- 部分国产 ROM 对前台服务限制激进，保活是持续性的适配工作。
- 路径规划 API 有调用配额，免费额度有限。

**合规与用途边界**
- 本工具的合理用途：**开发测试**、定位类 App 的 QA、隐私保护（不暴露真实位置）。
- 用于考勤打卡作弊、游戏外挂、欺诈、伪造物流轨迹等，属于违规甚至违法行为，**必须明确禁止**。
- 地图数据须使用合规图源，坐标系须符合国家规范；不得标注军事禁区、涉密单位或未公开的敏感坐标。
- 涉及用户位置数据时须遵守《个人信息保护法》：位置数据默认本地存储，不得收集、上传或公开他人位置。

---

## 十、结论

这条路**技术上可行，但只对 Android 成立**。三个真正的技术难点按重要性排序：

1. **坐标系转换**（中国区，做不对全盘皆错）
2. **后台保活稳定性**（决定用户是否会弃用）
3. **拟真度**（决定能不能通过目标 App 的检测）

建议第一步：用 Kotlin 写一个最简 Demo，只做 M1（定点模拟），先把"授权 → 注册 test provider → 写入坐标 → 目标 App 读到"这条链路跑通，验证可行性后再逐层加功能。
